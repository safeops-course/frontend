# Frontend Telemetry

What the browser sends, and where to find it.

## Scope

- browser traces (OpenTelemetry Web SDK)
- automatic HTTP spans for `fetch` and XHR calls
- UI spans around user actions, through `withSpan(...)`
- error details on the active span, from the axios interceptor

## Initialization

- `src/main.js` calls `initTelemetry()` before `app.mount(...)`.
- `src/services/telemetry.js` builds a `WebTracerProvider` with an `OTLPTraceExporter` and a
  `BatchSpanProcessor`.
- Resource attributes:
  - `service.name=frontend`
  - `service.version` - `VERSION` from the runtime config: the image's own tag (the Dockerfile sets
    `ENV VERSION=${APP_VERSION}`), unless the Deployment overrides it
  - `deployment.environment.name` - `ENVIRONMENT` from the runtime config (the same attribute the
    backend sends)

## Where spans go

The runtime config (`/config.js`, generated by nginx at container start from the environment) decides:
- `VITE_UPTRACE_DSN` set: spans go to `https://api.uptrace.dev/v1/traces` with the DSN in the
  `uptrace-dsn` header.
- otherwise `VITE_OTEL_COLLECTOR_URL`, if set.
- neither: spans are created - so the trace context still reaches the backend - but not exported. There
  is no default collector: a fallback to `http://localhost:4318` used to make every visitor's browser
  call a port on their own machine.

The image's CSP (`nginx/security-headers.conf`, `connect-src`) allows only `'self'` and
`https://api.uptrace.dev`; `allowedCollectorUrl` refuses other collector origins in production builds.

The OTLP exporter does not compress in the browser (gzip exists only in its Node.js transport), so no
`compression` option is set.

## Instrumentations

- `FetchInstrumentation`, `XMLHttpRequestInstrumentation`
- `DocumentLoadInstrumentation`
- `UserInteractionInstrumentation` (`click`, `submit`)

Not traced: `/healthz`, `/readyz`, `/livez`, `/metrics` (the dashboard polls them).

## Trace propagation

The browser adds `traceparent`, `tracestate` and `baggage` to requests whose URL matches
`propagateTraceHeaderCorsUrls`: `localhost`, `*.local`, `*.svc.cluster.local`, `*.safeops.work`, and the
origin of `VITE_API_URL`. The API is reached on the same origin (`/api/`, proxied by nginx), so one
trace runs from the click through the backend to its database queries.

## Errors on spans

- `withSpan(...)`: on an exception, `recordException`, status ERROR, and `error.type`, `error.message`,
  `http.url`, `http.request.method`, `http.response.status_code`, `app.error.detail` (the backend's
  `{"error": ...}`).
- axios interceptor (`src/services/api.js`): on a response error, the same on `trace.getActiveSpan()`.
  Network errors and 5xx from the probe endpoints above are not reported, so a backend restart does not
  flood Uptrace.

## UI spans

`withSpan(...)` is used in `src/stores/backend.js`, `src/views/ApiExplorerView.vue`,
and `src/views/ChaosView.vue`. Span names follow `ui.<view>.<action>`,
e.g. `ui.dashboard.fetch_version`, `ui.chaos.trigger_panic`, `ui.api_explorer.test_endpoint`.

The dashboard polls every 5 seconds while its tab is visible and stops when it is hidden.

## Configuration

Runtime (`/config.js`, from the container environment): `VITE_UPTRACE_DSN`, `VITE_OTEL_COLLECTOR_URL`,
`VITE_API_URL`, `ENVIRONMENT`, `VERSION`.

## Quick check

1. The browser console shows `OpenTelemetry initialized successfully`.
2. An action in the UI (a test request in the API Explorer) appears in Uptrace as a `ui.*` span, with
   the backend's `GET ...` span and its database spans in the same trace.
3. A backend error shows `http.url`, `http.response.status_code` and `app.error.detail` on the span.
4. With the backend down, the health and metrics polling does not flood Uptrace with exceptions.
